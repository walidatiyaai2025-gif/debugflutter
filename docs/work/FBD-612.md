# FBD-612 — Detect common Dart entry targets

Status: REVIEW

Issue: #114
PR: #115

## Goal

Enumerate likely Flutter/Dart entry targets from the successful FBD-601 project root without executing Flutter or Dart.

## Detection rules

- scan only within the resolved project `lib` directory
- identify canonical `lib/main.dart`
- identify common flavor/environment naming conventions: `main_<hint>.dart`, `main.<hint>.dart`, and `main-<hint>.dart`
- identify nested `main.dart` files within the bounded scan depth
- derive `FlavorHint` only from the conventional filename suffix; no semantic flavor is invented
- inspect each main-like candidate for a top-level `main(...)` declaration
- support common sync, async, argument, and arrow-body main signatures
- ignore `main` lookalikes inside comments, normal/raw/triple-quoted strings, and class/nested scopes
- expose normalized project-relative target paths such as `lib/main_dev.dart`
- preserve filename-only candidates with no top-level main as explicit non-runnable evidence
- within each scanned directory, inspect candidates by semantic priority so canonical `lib/main.dart` is retained before conventional flavor or nested targets when the candidate cap is reached

## Scan safety

- maximum recursive depth below `lib`: 4
- maximum visited directories: 256
- maximum main-like candidates: 128
- maximum source size inspected per candidate: 512 KiB
- project root and `lib` reparse/symlink boundaries are rejected
- reparse/symlink child directories are not traversed
- reparse/symlink candidate files are preserved as unsafe/non-runnable evidence and are not read
- excessive depth/candidate/directory conditions are surfaced explicitly rather than silently truncated
- no project mutation and no raw Dart source exposure through the result contract
