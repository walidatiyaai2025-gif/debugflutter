# FBD-611 — Detect product flavors

Status: IN PROGRESS

Issue: #112

## Goal

Enumerate statically configured Android product flavors from the exact FBD-604 Android app Gradle script without executing Gradle or expanding build variants.

## Detection rules

- inspect only direct `android { productFlavors { ... } }` declarations
- support Groovy named flavor blocks such as `demo { ... }`
- support container calls such as `create("demo") { ... }` and `register("demo") { ... }`
- parse static top-level `flavorDimensions` declarations in common Groovy/Kotlin forms
- parse per-flavor static `dimension`, `applicationId`, `applicationIdSuffix`, and `versionNameSuffix`
- when exactly one static flavor dimension is declared and there are no unresolved dimension declarations, infer that dimension for a flavor that omits it
- preserve dynamic/non-literal flavor names and field declarations explicitly as unresolved instead of guessing
- repeated identical static values are accepted; conflicting static values or duplicate static flavor names are ambiguous
- helper container blocks such as `all {}` and `configureEach {}` are not treated as flavor names

## Scope boundary

- FBD-611 does not expand build variants or combine product-flavor metadata with build-type suffixes
- it does not evaluate Gradle/Groovy/Kotlin expressions
- it does not execute Gradle/gradlew
- it does not mutate project files
- it does not expose raw Gradle source through the result contract

## Safety

The detector revalidates the expected `android/app/build.gradle` or `build.gradle.kts` path supplied by FBD-604 and rejects stale, wrong-role, reparse/symlink, or scripts larger than 512 KiB before parsing.

## Coverage

Tests cover common Groovy and Kotlin flavor declarations, static metadata, single-dimension inference, multiple dimensions, Kotlin `listOf` dimensions, dynamic flavor names, static+dynamic field conservatism, conflicting declarations, duplicate names, comments/string lookalikes, build-type exclusion, helper container blocks, no-flavor projects, empty suffixes, unresolved dimension declarations, path injection, stale evidence, symlinks, oversized scripts, wrong script roles, no-raw-source contract, and singleton DI composition.

## Validation

GitHub Actions on the feature branch and pull request is the authoritative build/test gate because the current local execution environment does not provide the .NET SDK.
