# FBD-311 — Recover repository refresh from locked workspace files

Issue: #37

## Problem

Repository Manager already uses the FBD-309 safe refresh sequence: verify the existing repository, clone to a sibling staging directory, verify staging, move the original to a preserved backup, promote staging, then verify/rollback as needed.

On Windows, the original-to-backup move can fail after a successful clone when another process has an open file handle under the repository:

`Existing repository could not be moved to backup: The process cannot access the file because it is being used by another process.`

That left the verified staging clone cleaned up and required the user to manually find/stop the lock owner before retrying.

## Implementation

- Added `IGitWorkspaceLockResolver` and `WindowsRestartManagerWorkspaceLockResolver`.
- Uses the Windows Restart Manager API (`rstrtmgr.dll`) to discover processes that actually own handles to files in the repository.
- Registers preferred Git/Flutter metadata first, then repository files, in bounded batches.
- Terminates every discovered lock owner except the current Flutter Build Doctor process and protected critical Windows processes.
- Uses `Process.Kill(entireProcessTree: true)` and waits for process exit so child build/tool processes do not keep the workspace locked.
- Added `LockRecoveringGitRefreshFileSystem`, which decorates the existing FBD-309 filesystem boundary.
- A directory move is attempted normally first. Only an `IOException`/`UnauthorizedAccessException` triggers lock recovery.
- After lock recovery, the exact same move is retried with bounded backoff. If it succeeds, FBD-309 continues normally into promotion and final verification. If it still fails, the existing `BackupFailed` path receives lock-recovery evidence.
- Production DI now uses the lock-recovering filesystem while preserving `GitRepositoryRefreshService` and its backup/rollback semantics unchanged.

## Safety boundaries

- No blanket process-name kill list is used; the resolver asks Windows which processes own handles to this repository.
- Flutter Build Doctor never kills itself.
- PID 0-4 and critical Windows process names are protected.
- No original repository content is deleted to solve a lock.
- The verified staging/backup/rollback transaction remains authoritative.
- If lock recovery cannot safely resolve the owner, refresh fails instead of discarding the original repository.

## Coverage

- Unit: first directory move locked -> resolver called -> bounded retry succeeds.
- Unit: persistent lock -> retry budget exhausted -> evidence preserved in exception.
- Unit: ordinary successful move -> resolver is never invoked.
- Composition: production DI resolves the Windows lock resolver and `LockRecoveringGitRefreshFileSystem`.
- Windows integration: a real child PowerShell process opens a repository file with `FileShare.None`; Restart Manager identifies the child, terminates it, and the repository directory can then be moved.
