# FBD-602 — Parse pubspec.yaml

Status: DONE pending final PR-head CI and merge

## Scope

Parse the effective `pubspec.yaml` returned by FBD-601 into typed, read-only project metadata and dependency evidence. Do not read `pubspec.lock`, resolve packages, run Flutter/Dart/pub commands, or modify repository files.

## Implementation

- Added `IPubspecParser`, typed parse statuses, metadata, dependency sections, and dependency kinds.
- Uses YamlDotNet representation-model parsing; no arbitrary object construction/deserialization.
- Requires a successful FBD-601 result and verifies the effective pubspec is the direct `pubspec.yaml` child of the effective root.
- Enforces a 2 MiB file-size safety limit before reading.
- Rejects pubspec reparse points/symbolic links before reading so parsing does not follow external file targets.
- Requires exactly one YAML mapping document and validates known pubspec field/section shapes before projection.
- Preserves raw pubspec text for malformed/invalid document evidence after a bounded read.
- Extracts package name, description, version, publish target, project URLs, Dart/Flutter SDK constraints, topics, dependencies, dev dependencies, and dependency overrides.
- Projects hosted, SDK, path, git, and unknown dependency specs while retaining their relevant constraints/evidence.
- Sanitizes structured URL evidence by removing embedded credentials, query strings, and fragments. Raw text remains parser evidence and must not be logged as a secret-safe field.
- Registered `IPubspecParser` in production DI.

## Safety and boundaries

- No repository mutation.
- No `pubspec.lock` read or write; FBD-603 owns lockfile parsing.
- No version compatibility decisions; later analyzer/compatibility tasks own those policies.
- No Flutter, Dart, pub, Gradle, or network command execution.
- Wrong known YAML shapes return `InvalidDocument` instead of being silently treated as empty sections.
