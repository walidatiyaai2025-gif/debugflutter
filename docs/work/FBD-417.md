# FBD-417 — Environment Doctor dashboard UI

Status: DONE

## Scope

Present the immutable `EnvironmentSnapshot` from FBD-416 in the WPF shell. Each environment component must expose state, path, version, and a user-readable next action. This task is presentation-only: it does not repair the machine and does not implement explicit refresh/re-scan behavior.

## Implementation

- Added `EnvironmentDoctorViewModel`, consuming only `IEnvironmentSnapshotService`.
- Added a read-only `EnvironmentComponentViewModel` presentation record.
- Projects one snapshot into 14 component cards:
  - Windows
  - environment variables
  - Flutter SDK
  - Dart SDK
  - Java/JDK
  - Android SDK
  - command-line tools
  - ADB/platform-tools
  - installed Android platforms
  - installed Android build-tools
  - Android emulator
  - avdmanager
  - Android licenses
  - Android Studio
- Every card exposes state, detector status detail, path, version, and next action.
- Added dashboard summary counts, capture timestamp, capture duration, loading state, and failure status.
- Registered `EnvironmentDoctorViewModel` in presentation DI and exposed it from `MainWindowViewModel`.
- Replaced the static `Not scanned` placeholders in `MainWindow.xaml` with the Environment Doctor dashboard.
- Performs one initial environment capture when `MainWindow` first loads.
- Initial loading is deliberately idempotent so FBD-418 remains the owner of explicit refresh/re-scan behavior.

## Safety boundaries

- No PATH/JAVA_HOME/ANDROID_HOME/ANDROID_SDK_ROOT mutation.
- No SDK, JDK, Flutter, Android Studio, license, Git, or cache repair.
- No detector orchestration is duplicated in the ViewModel; it consumes FBD-416 only.
- No refresh command is introduced in FBD-417.

## Coverage

`EnvironmentDoctorViewModelTests` verifies:

1. A snapshot maps to all 14 state/path/version/action cards.
2. The initial scan is idempotent until FBD-418 adds explicit refresh.
3. Capture failures are surfaced without falsely claiming a loaded environment.
