# FBD-609 — Parse applicationId / namespace

Status: IN PROGRESS

Issue: #108

## Goal

Extract the Android namespace and default application ID from the exact FBD-604 Android app Gradle script without executing Gradle or guessing dynamic expressions.

## Implementation

- added `IAndroidIdentifierParser` with typed status, values, evidence, and unresolved-field reporting
- supports static Groovy and Kotlin DSL `namespace` and `defaultConfig.applicationId` declarations, including assignment, Groovy-style literal call, and parenthesized literal forms
- keeps `namespace` scoped to the direct `android { ... }` body and `applicationId` scoped to direct `defaultConfig { ... }` bodies
- intentionally excludes flavor/build-type overrides from FBD-609; flavor analysis remains FBD-611
- ignores comments, quoted examples, nested lookalikes, and `applicationIdSuffix`
- reports dynamic expressions, interpolation, concatenation, malformed/non-literal values, and unsupported string forms as unresolved instead of guessing
- accepts repeated identical static declarations and returns `Ambiguous` for conflicting values of the same field
- allows namespace and applicationId to differ because that is valid Android project evidence, not a conflict
- revalidates the exact FBD-604 app script path and rejects stale, reparse/symlink, wrong-role, or oversized evidence
- exposes no raw Gradle script text and registers the parser as a production singleton

## Safety boundary

FBD-609 performs bounded read-only static Gradle inspection only. It does not execute Gradle/gradlew, evaluate Groovy/Kotlin expressions, resolve version catalogs, inspect signing secrets, mutate project files, or infer flavor-specific IDs.

## Coverage

Unit coverage includes Groovy/Kotlin literals, namespace/applicationId divergence, parenthesized calls, dynamic expressions, interpolation, concatenation, duplicate/conflicting declarations, comments/string lookalikes, suffix exclusion, strict DSL scoping, missing app-script evidence, and the no-raw-source contract. Boundary coverage validates injected paths, stale evidence, symlinks/reparse points, and oversized scripts. Composition coverage verifies singleton DI registration.
